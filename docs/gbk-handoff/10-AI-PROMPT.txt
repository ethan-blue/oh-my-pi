三、已经确定的方向

直接改 OMP Core，原地处理现有 GBK 文件，保留 Rust 编辑引擎和 Hashline 算法。
不做虚拟盘，不做 WSL 转换，不做 UTF-8 工程副本同步，不退回只覆盖几个工具的 Extension。
默认不开启编码适配时保持原版 UTF-8 行为；GBK 只作用于明确配置的项目源码路径。
统一 codec/策略，避免各工具分别实现一套编码猜测。
当前编辑和快照核心已在 crates/pi-edit；不能只改 TypeScript 或 Bun.write。

四、编码与完整性要求

1. 明确项目/路径规则优先，不宣称自动识别所有编码。
2. 新增 Fork 专用项目策略文件的具体 schema 按 02 实现并测试；文档示例当前不是已存在配置能力。
3. 严格解码、严格编码；遇非法字节或 GBK 无法表示字符时写前报错，不能替换成问号、U+FFFD 或 HTML 实体。
4. 不把 GBK 悄悄升级为 GB18030；未实现的编码明确拒绝。
5. 保留原编码、BOM、CRLF/LF、末尾换行和未修改字节；混合换行无法保留时明确拒绝写入。
6. read、grep、AST、Hashline 快照、edit 必须看到一致的文本。
7. AST UTF-8 偏移和 LSP position encoding 不得当成 GBK 字节偏移。
8. 保留 stale edit、权限、plan mode、symlink、取消和缓存失效语义。
9. 多文件先预检、保留原始 bytes 和恢复信息；不得将单文件原子替换称为全批次原子。
10. codec、字节元数据和落盘应有明确边界；不要把 N-API 设计成每行一次 JS 回调。

# R10 — 原生工具编码失败后绕过编辑链路（P1）

更新日期：2026-10-09。状态：用户报告的使用事故；待实现、待复现验收。与 R01—R09 一起进入修复队列，不代表已修复。

## 1. 事实与证据边界

用户提供的 Agent 自述：修改 `tests/verify_static_layout.py` 和 `tests/test_single_pos_cases.c` 时，未被 `.omp/encoding.json` 覆盖的 `.py` 文件触发 UTF-8 解码错误；Agent 随后用 bash 执行 `python -c` 和 `open(...).write(...)` 改写文件，并用 Python 代替原生 read/grep 进行检索、生成属性表和排查。

用户要求：源码、测试及属性表等任务文件的编辑使用原生 edit/write；源码读取检索使用原生 read/grep/glob；允许原生 GCC/Keil 编译验证，不用 Python 脚本代替文件操作。

已核实 `packages/coding-agent/src/prompts/system/system-prompt.md:121` 原本就包含禁止 sed/perl/python 经 bash 作单文件编辑的规则。因此，本项不能仅增加一段提示词或要求 Agent 检讨就宣称完成。

未获得该工程、原始字节和工具调用日志；尚未确认实际文件编码、Python 参数、是否发生编码/换行变化。用户报告不等于本仓库复现，也不能直接断言文件已损坏。两个路径作为事故验收用例名称，不假定它们位于 ompg 仓库。

## 2. 修复目标与边界

1. 原生工具失败后提供可恢复路径，不能迫使 Agent 为完成任务另找文件写入通道。
2. 对该项目明确启用“原生文件工具优先且受约束”的模式；普通原版兼容模式保留现有选择，不能把本项目限制强加给所有用户。
3. 受保护模式下，Agent 不得通过 bash/Python/PowerShell/Node/eval、子 Agent、ACP 或扩展变相修改受保护源码。模式必须在工具执行前检查，不能只在模型提示词中表达。
4. 任意外部进程本身不经过 Core。实现初版可关闭任意 shell/eval，只提供明确配置的构建任务入口；若当前平台无法隔离可信构建进程的写入权限，必须如实说明“限制 Agent 可调用入口，构建程序仍受信任”，不得声称操作系统级全局防写。
5. 不引入虚拟盘、WSL 镜像或 UTF-8 工程副本同步；不通过全项目转 UTF-8 消除错误。

## 3. A — 编码诊断与原生恢复（依赖 R01—R04）

入口：`packages/coding-agent/src/encoding/index.ts`、`crates/pi-edit/src/encoding.rs`、`crates/pi-edit/src/files.rs`、`packages/coding-agent/src/tools/read.ts`、`src/edit/index.ts`、`src/tools/write.ts`。

- 不把 `.c/.h` 当成 GBK 的唯一范围，`.py/.inc/.rc` 和测试目录同样由实际字节及明确路径规则决定；不得直接把所有 `.py` 配成 GBK。
- 原生读取遇到未管理且非法 UTF-8 的文件，返回结构化原因，至少区分：规则未覆盖、已选编码下非法字节、BOM/规则冲突、不支持的编码、输出字符不可表示。说明有效 root、命中的规则或未命中、失败偏移；不得泄露整份源码。
- 诊断只用内置字节读取与 codec。可展示严格 GBK 解码和字节往返检查得到的候选结果，但“能解码”不是编码确定证据；ASCII 也不能证明原编码。
- `.py` 第一/第二行编码声明可作为诊断证据；按语言声明规则识别，不执行 Python、不盲扫任意注释。声明、BOM、项目规则冲突时明确失败。
- 如已有用户授权/可信项目约定能确定编码，可用原生 edit/write 为确切路径补齐 include/override；仅有候选且有歧义时，保留文件并询问编码选择。不要为每次普通编辑重复确认，也不能自行选择不确定编码。
- 修正规则前展示影响路径；修改后失效缓存及旧快照，重新 read 获取 Hashline 锚点，再执行原 edit。`.omp/encoding.json` 自身始终以 UTF-8 管理，避免新文件默认 GBK 污染控制文件。
- 明确错误恢复建议：“补充正确的项目编码规则后重读”，不得建议 Python 重写、忽略错误、替换字符或整体转码。

## 4. B — 统一的工具权限执行点（依赖 P09）

审计入口：`packages/coding-agent/src/tools/index.ts`、`src/tools/bash.ts`、`src/tools/bash-interceptor.ts`、`src/exec/bash-executor.ts`、`src/eval/index.ts`、`src/eval/executor-base.ts`、`src/eval/py/executor.ts`、`src/eval/js/executor.ts`、`src/task/executor.ts`。实现前定位所有实际分派点，不假定只覆盖这些文件即可。

- 复用现有权限/工具注册机制，增加项目级有效能力约束；不要再造一套与已有 approval/plan mode 冲突的系统。
- 受保护模式不给 Agent 自由 bash/Python/PowerShell/Node/直接文件系统 eval 权限。对不可验证的命令在启动进程前拒绝；隐藏工具只能改善选择，不是执行层授权。
- 构建使用结构化任务 ID 和预配置的可执行程序/参数/工作目录/输出路径；禁止模型把自由 shell 字符串包装成“编译”。GCC/Keil 参数、响应文件、插件、自定义 hooks 和构建脚本均需纳入信任边界；编译器白名单本身不等于源码只读。
- 可隔离时，构建进程读取源码、只写指定 build/artifact 目录；不可隔离时明确可信构建例外，未经授权不让 Agent改写任务、响应文件或 hook 来扩大权限。
- 原有生成器确需更新受跟踪源码时，作为单独明确授权能力处理，不以“编译成功”为由默认放行任意源码写入。
- 子 Agent、SDK/ACP 执行、工具覆盖、扩展、动态新增工具继承同一项目约束。来源不明的新写入能力默认拒绝；Agent 不能编辑 `.omp/encoding.json` 或其他普通工程文件来关闭外部执行限制。
- 编码失败不能临时扩大能力，也不能改用 write 绕过已有文件的严格解码、原字节校验和并发检查。
- 项目要求只用 read/grep/glob 检索时，同样不提供 Python 的通用读取代劳路径；原生工具能力不足就修工具或明确报告限制。
- 日志记录被拒绝的工具类别、策略、目标和结果，避免记录脚本中的源码/密钥。写后 hash 只能作为监测证据，不能充当预防机制或静默回滚外部用户修改。

## 5. C — 事故恢复与使用体验

按“原生 read/edit 失败 → 显示规则缺口 → 原生修正规则 → 重新 read → 原生 edit → 编译验证”完整闭环验收。界面/模型得到的信息要足够继续任务，而不是只收到 InvalidUtf8。

对实际事故工程，先读取 Git 状态、diff、可用备份和当前字节，确认两个文件是否被改编码、BOM、换行或截断。与最近可信版本比较时保留事故后有效代码修改；不得直接 checkout/reset 覆盖用户工作。恢复通过原生工具在临时候选中验证后应用，没有可信原件就标明无法证明原始字节。

属性表若是项目源码/测试产物，使用原生 write 创建、edit 修改并严格编码；原生表生成能力不足应纳入工具需求，不授权临时 Python 写入绕过。
